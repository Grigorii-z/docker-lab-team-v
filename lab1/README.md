# ЛР 1. Dockerfile

Приложение — Jupyter Lab, запуск с volume:

```bash
docker build -f Dockerfile.good -t lab1-good .
docker run -d -p 8888:8888 -v jupyter_data:/home/jovyan/work lab1-good
```

## Плохие практики

1. **`FROM python:latest`.** Тег latest меняется со временем, поэтому сборка невоспроизводима, а полный образ к тому же тяжёлый и содержит много лишнего. Нужно `FROM python:3.12-slim` используем фиксированную версиб и минимальный образ.
2. **Отдельные `RUN apt-get update` и `RUN apt-get install` с ненужными пакетами.** Каждый `RUN` создаёт новый слой, закэшированный `update` может дать устаревший индекс пакетов, а `vim`, `curl`, `git` для Jupyter не нужны и раздувают образ. Правильно убрать лишние пакеты, если они нужны, их ставят одним `RUN` через `&&` с очисткой кэша apt.
3. **Запуск от root.** Ядро у контейнера с хостом общее, поэтому при уязвимости атакующий получает root-права.
Правлиьно создать пользователя jovyan, приложение запускается через USER jovyan.

## Плохие практики использования контейнера

1. **Хранить данные внутри контейнера, без volume.** Writable слой удаляется вместе с контейнером, и ноутбуки пропадут, данные нужно хранить в volume.
2. **Запускать контейнер с `--privileged` или монтировать системные директории хоста** Jupyter выполняет произвольный код, так что это фактически даёт доступ к хосту.

## Когда не стоит использовать контейнеры

1. **Высоконагруженные БД в продакшене.** Контейнеры рассчитаны на stateless приложения, а лишние абстракции ухудшают latency и работу с дисками.
2. **Нужна полная изоляция или другое ядро/ОС.** Контейнеры делят ядро хоста, поэтому для строгой изоляции, другой ОС или legacy систем лучше подходит виртуальная машина.
